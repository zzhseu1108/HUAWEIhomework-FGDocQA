# DocQA 技术设计说明书

> 版本：v1.0 · 对应代码：`src/docqa/` · 更新日期：2026-10-24
>
> 本文回答三个问题：**系统怎么分层、层与层之间靠什么契约通信、关键算法如何实现。**

---

## 1. 设计范围与原则

### 1.1 范围

覆盖 DocQA 的五条主链路：

1. 多模态文档解析（`doc2md`）；
2. 语义切片与三路索引（`docbase.indexer`）；
3. 三路召回、RRF 融合与精排（`docbase.retriever`）；
4. Agent 问答编排与强制溯源（`agent.answer`）；
5. 可选的服务化入口（`service.watcher`、`web.server`）。

### 1.2 设计原则

| 原则 | 落地方式 |
| --- | --- |
| 分层单向依赖 | `web/service → agent → docbase → doc2md → llm`，禁止反向 import |
| 契约稳定 | 跨层只经 `models.py`；字段只增不改 |
| 模型可替换 | 四类端点统一由 `ModelHub` 注入；Mock 可离线跑通 |
| 证据优先 | 回答只使用检索到的 Chunk；不足即拒答 |
| 可核对 | 每个 Chunk 带 doc/page/heading/source；图片额外带 fig/title |
| 可回滚 | 索引版本化；`index.json + vectors.json + sparse.json` 三件套 |
| 无重依赖 | 运行时仅标准库；PDF 解析可选 `pypdf` |

---

## 2. 总体架构

```text
┌──────────────────────────────────────────────────────────────┐
│ 入口层  CLI / Web / Service(watcher)                          │
├──────────────────────────────────────────────────────────────┤
│ Agent 层  answer_question：意图 → 检索 → 自评 → 生成 → 引用   │
├──────────────────────────────────────────────────────────────┤
│ 检索层  DocBase：chunk / build / query / RRF / rerank / eval  │
├──────────────────────────────────────────────────────────────┤
│ 解析层  doc2md：PDF/Word/PPT/MD → Markdown + 图片释义 + manifest│
├──────────────────────────────────────────────────────────────┤
│ 模型端点层  VL / Embedding / Reranker / Chat（可 HTTP / Mock） │
└──────────────────────────────────────────────────────────────┘
```

依赖方向自上而下；`models.py` 是各层之间唯一的数据通道。

## 3. doc2md 解析层

### 3.1 入口与分发

```python
parse_document(src, out_dir=None, category=None, hub=None, options=None) -> ParseResult
```

- 通过扩展名 + 文件头识别类型（PDF `%PDF`、OOXML `PK` + `word/`/`ppt/`）；
- 支持 `.md/.markdown`、`.pdf`、`.docx`、`.pptx`、`.txt/.text/.log`；
- 输出目录固定包含：
  - `document.md`：带 front matter 的结构化 Markdown；
  - `assets/`：按溯源规范重命名的图片；
  - `manifest.json`：解析任务、图片清单、统计、警告。

### 3.2 Markdown 解析

逐行扫描：

1. `<!-- page: N -->` 更新当前页码；
2. `![alt](path)` 解析本地图片：
   - 相对路径 → 源文件目录；
   - 复制到 `assets/`，按 `文档名_Page{N}_Fig{k}_{标题}.ext` 命名；
   - 调 VL 释义；
   - 在原位置替换为「图片 + 引用块 + 元信息注释」；
3. 标题、正文、表格原样保留；
4. front matter 重新生成（doc_id / source / pages / page_mode / category / parsed_at）。

图片写回格式：

```markdown
![图题](assets/文档名_Page2_Fig1_图题.png)

> **图 2-1 · 图题**（VL 释义）：……图中模块与箭头……该图位于《文档名》第 2 页……

<!-- docqa:image path=assets/... page=2 figure=1 title=图题 -->
```

### 3.3 PDF 解析

- 使用 `pypdf` 逐页 `extract_text()`；PDF 取图需 `Pillow`；
- 每页写入 `<!-- page: N -->`，页码 **exact**；
- `page.images` 提取嵌入位图，写入当前页；
- 图题从页内最后几行中匹配 `图 N` / `Figure N`；
- 矢量图（PDF drawings）当前版本不直接渲染，记录告警；扩展点见 §11；
- 无 `pypdf` 时给出明确安装提示，不静默失败。

### 3.4 DOCX 解析

不依赖 `python-docx`，直接解析 OOXML：

- 读取 `word/document.xml`、`word/_rels/document.xml.rels`、`word/media/*`；
- 段落：`w:p` → `w:t` 拼接；`w:pStyle` 识别 Heading/标题；
- 图片：`a:blip` 的 `r:embed` → rels → media；
- 表格：`w:tbl` → GFM 表格；
- 分页：`w:br type="page"` 与 `w:lastRenderedPageBreak` 估算页码；
- `page_mode = estimated`，在 manifest/回答中明示。

### 3.5 PPTX 解析

- `ppt/slides/slideN.xml` 按编号排序，一页幻灯片 = 一页；
- 段落 `a:p` → `a:t`；第一段作为标题；
- 通过 `ppt/slides/_rels/slideN.xml.rels` 提取图片；
- 页码 **exact**，输出 `## Slide N` + 列表 + 图片块。

### 3.6 图片与溯源命名

```text
文档名_Page{页码}_Fig{图序}_{Figure标题}.{ext}
```

- 图序按页内计数；
- 标题优先取图注（`图 1 ...`），否则取 alt；
- 移除路径分隔符、空格，保留中文；
- `ImageInfo.source_uri` 形如 `file:///.../doc.md#page=2&figure=1`；
- 图片释义与原文页码、图题、原图路径绑定，支持「图文互证」。

### 3.7 VL 释义协议

**真实端点**（OpenAI-compatible）：

```json
POST {base}/chat/completions
{
  "model": "Qwen3.6-27B-VL",
  "messages": [{
    "role": "user",
    "content": [
      {"type": "text", "text": "请描述图中模块/箭头/编号/关键文字…"},
      {"type": "image_url", "image_url": {"url": "data:image/png;base64,..."}}
    ]
  }]
}
```

Prompt 要求：客观描述模块、连线方向、编号步骤、关键数值；不臆造；220 字内。

**Mock 模式**：用作者提供的图注/alt + 版式关键词生成可复现释义，并在文末标注「离线 Mock 释义」。Mock 不替代真实读图能力，只保证离线链路与测试可跑。

### 3.8 失败与降级

| 场景 | 行为 |
| --- | --- |
| 图片不存在 | 保留原引用 + warning |
| EMF/WMF/SVG/TIFF | 跳过读图 + warning（需先渲染） |
| VL 端点失败 | 回退 Mock 释义 + 记录 warning |
| PDF 取文/取图失败 | 该页为空 + warning，不中断整篇 |
| 不支持的格式 | 抛 `ValueError`，CLI 返回非 0 |

## 4. DocBase 检索层

### 4.1 语义切片

`chunk_markdown(text, doc_meta, images, chunk_size=1200, overlap=120)`

- 以标题与页码为边界：**一个 Chunk 不跨页**，保证引用页码准确；
- 按空行切段落；段落超长时按句子切；
- 代码块/Mermaid 保持原子性；若与前文合计不超限，则合并到同一 Chunk（让流程步骤与流程图同块）；
- Chunk 文本前缀 `【标题路径】`，保留章节语义；
- 附带该块引用到的图片元数据（`images`）；
- 过短块（< 20 字）丢弃，避免噪声。

Chunk 字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `chunk_id` | str | `sha1(doc_id:order:text)[:16]` |
| `doc_id` | str | 文档稳定标识 |
| `doc_name` | str | 文档名 |
| `heading` | str | 标题路径，如 `A / B / C` |
| `text` | str | 含标题前缀与图片释义的检索文本 |
| `page` | int | 起始页码 |
| `category` | str | 分类 |
| `source_path` | str | 原始文档绝对路径 |
| `source_uri` | str | `file://...#page=N` |
| `order` | int | 文档内顺序 |
| `images` | list | 关联图片元数据 |
| `content_hash` | str | 文本哈希 |
| `char_count` | int | 字符数 |

### 4.2 Tokenizer

无第三方分词依赖，混合中英文：

- ASCII：`[a-zA-Z0-9][a-zA-Z0-9_.\-/#]*`，小写；
- 中文：连续汉字段的 **字符 bigram**（单字段保留单字）；
- 过滤停用词与疑问词。

同一 tokenizer 用于 BM25、稀疏向量、Mock Embedding 与 Mock Reranker，保证离线一致性。

### 4.3 稠密向量

- 真实模式：`POST {base}/embeddings`，模型 Qwen3-Embedding-8B；
- Mock 模式：512 维 hashing embedding：
  - 对每个 token 做 MD5，取前 4 字节映射到维度，第 5 字节决定符号；
  - 权重 `1 + ln(tf)`，L2 归一化；
  - 优点：确定性、零依赖；缺点：**不具备真正语义泛化**，仅用于离线闭环。

相似度：余弦。

### 4.4 BM25

参数 `k1=1.5, b=0.75`：

```text
IDF(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
score(q, d) = Σ_t IDF(t) * tf(t,d) * (k1 + 1)
              / (tf(t,d) + k1 * (1 - b + b * |d| / avgdl))
```

其中 `N` 为 Chunk 数，`df` 为文档频率，`|d|` 为 Chunk token 数，`avgdl` 为平均长度。

### 4.5 本地稀疏向量

本地 TF-IDF 词法稀疏表示（`tfidf-local / lexical`，不是 BGE-M3 学习型稀疏权重）：

```text
w(t) = (1 + ln tf(t)) * IDF(t)
向量 L2 归一化
score = cosine(query_weights, chunk_weights)
```

存储为 `[[token, weight], ...]`，查询时用同一 IDF 计算 query 权重。

### 4.6 RRF 融合

每一路取前 50，按排名融合：

```text
RRF(d) = Σ_r 1 / (60 + rank_r(d))
```

`k=60`；同一 Chunk 在多路出现则累加。融合后取前 `max(24, top_k*4)` 进入精排。

### 4.7 精排

- 真实模式：`POST {base}/rerank`，模型 Qwen3-Reranker-8B；
- Mock 模式：`0.62 * token 覆盖率 + 0.28 * 精确术语命中率 + 0.10 * 首段命中`；
- 最终分：

```text
final = 0.72 * normalize(rerank) + 0.28 * normalize(RRF)
```

若 rerank 全为常数，则退化为 RRF 排序。

### 4.8 索引落盘

```text
data/index/
├── index.json    # RagIndex：版本、文档注册表、Chunk 清单、统计
├── vectors.json  # {"model": "...", "dim": 512, "vectors": {chunk_id: [...]}}
└── sparse.json   # {"N":..., "avgdl":..., "df":..., "vectors":..., "tf":...}
```

- 增量建库：按文档内容哈希判断是否变更；未变更文档复用旧 Chunk；
- 向量按 `chunk_id` 复用（内容寻址）；Embedding 模型变化时强制重算；
- 删除文档时，其 Chunk 不再进入新索引；解析目录中的陈旧产物由 watcher 清理；
- 索引版本：`YYYY.MM.DD-HHMMSS`，可用于回滚与审计。

### 4.9 评估（test 模式）

`evaluate(index_dir, test_set, top_k=6)`：

- 每个用例：`question` / `expected_docs` / `expected_keywords` / `category?`；
- `recall@k = 命中期望文档数 / 期望文档数`；
- `hit_rate = 是否至少命中一个期望文档`；
- `MRR = 1 / 首个相关结果排名`；
- `keyword_hit_rate = 命中关键词数 / 关键词数`；
- 输出 per-case + summary，落盘 JSON。

## 5. Agent 层

### 5.1 问答主流程

```python
answer_question(question, index_dir, max_rounds=2, top_k=6, category=None) -> Answer
```

1. **意图分类**：command / flow / version / troubleshoot / term / concept；
2. **Query 构造**：原问题 + 去疑问词/标点改写 + ASCII 术语补充；
3. **检索**：每个 query 调 DocBase，多 query 结果按 chunk_id 合并（取高分、RRF 累加）；
4. **充足性自评**：
   - 最高 `rerank_score >= 0.20`；
   - 问题 token 在 Top-3 Chunk 中的覆盖率 `>= 0.30`；
   - 不满足则用 Top-1 的标题扩展 query，进入第二轮；
5. **生成**：
   - 真实模式：GLM-5.1，严格 system prompt；
   - Mock 模式：抽取式合成（结论 + 步骤/表格/句子 + 引用）；
6. **结构化**：流程类附加 Mermaid；命令/参数类附表格；版本类附特性表；
7. **引用重编号**：只保留回答正文实际使用的引用，按首次出现重排 `[n]`；
8. **返回** `Answer`。

### 5.2 意图与检索策略

| 意图 | 触发词示例 | 优先证据形态 |
| --- | --- | --- |
| command | 命令、参数、配置、操作、CLI | 命令表、注意事项 |
| flow | 流程、步骤、转发、接续、时序 | 编号步骤、Mermaid |
| version | 版本、特性、发布、变更 | 特性表 |
| troubleshoot | 故障、排查、失败、告警 | 排查步骤 |
| term | 含型号/英文术语 | 术语定义、命令 |
| concept | 其他 | 段落/列表 |

### 5.3 抽取式合成规则

Mock 模式不调用 Chat，仍要保证可读与可核对：

- **流程**：取原文编号步骤 3 条以上 → 作为「关键依据」；原文有 Mermaid 则重绘；
- **排障**：取编号步骤，结论为「建议按以下步骤排查」；
- **命令**：选含「命令/反引号/reset」的句子作结论，附执行前注意事项；
- **参数**：优先表格行，结论取参数定义句；
- **版本**：取「新增特性」表行，按 `特性：说明（受益场景）` 格式化；
- **概念**：按 query token 覆盖率选句，去重后输出。

### 5.4 引用策略

- 每个 `[n]` 对应一个真实 `Chunk`；
- `Citation` 字段：`ref / doc_id / doc_name / page / heading / snippet / source_uri / source_path / figure`；
- 图片优先使用 `ImageInfo.source_uri`（带 `#page=&figure=`）；
- 回答正文只保留实际出现的引用，`溯源` 段按新编号重建；
- 无依据时 `citations=[]`，明确输出「无据不答」。

### 5.5 Prompt 约束

```text
你是 DocQA……
1. 存在性：本仓库配备 DocBase 库，回答前必须先检索；
2. 查询策略：技术名词优先精确检索，原理/流程优先语义检索；
3. 溯源强制：每个结论标注 [n]，给出文档名/页码/图号；不足时回答「无据不答」，禁止编造；
4. 产出形式：流程类给出 Mermaid，并提示与原图对照。
只依据提供资料回答。
```

## 6. 服务化入口

### 6.1 CLI

| 命令 | 作用 |
| --- | --- |
| `parse` | 解析单文件/目录 |
| `build` | 建库（`--incremental`） |
| `query` | 只检索，显示三路分数 |
| `ask` | 检索 + 生成 + 溯源；`--show-trace` |
| `eval` | recall@k / hit_rate / MRR |
| `serve` | Web 问答 |
| `watch` | 目录监控 + 增量更新 |
| `demo` | 一键跑通 |
| `doctor` | 环境/模型/索引检查 |

### 6.2 Web API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/health` | 存活检查 |
| GET | `/api/stats` | 索引统计、文档列表、模型模式 |
| GET | `/api/doc?doc_id=&mode=parsed` | `WebDocumentResponse`：解析后原文和图片溯源清单 |
| GET | `/api/asset?doc_id=&path=assets/...` | 预览该文档已入库的位图图片 |
| GET | `/api/search?q=&top_k=` | 只检索 |
| POST | `/api/ask` | `{question, top_k?, max_rounds?, category?}` → `WebQueryResponse` |

`WebQueryResponse` 与 `answer_question` 对齐：`answer / format / citations / rounds_used / sufficient / elapsed_ms / trace / mermaid`。

`WebDocumentResponse` 保留原文接口的 `doc_id / doc_name / category / page_mode / source / source_uri / text`，追加 `images`。图片按索引中该文档的 `Chunk.images.path` 去重，保留 `ImageInfo` 元信息；支持预览的位图额外附本机 `url`。图片接口只接受该文档索引中登记的路径，且解析后的真实路径必须位于文档自身 `assets/` 内；拒绝路径穿越、逃逸符号链接和非位图格式。Web 问答最多检索 2 轮。

前端由 `static/index.html`、`style.css`、`app.js` 组成，无构建步骤与 CDN 依赖。三个视图分别为智能问答、知识文库、我的收藏；浏览器 `localStorage` 保存最多 30 个会话和 100 条收藏（仅当前浏览器）。问答按当前问题独立检索；会话历史不作为模型上下文。异步回包绑定原会话，避免切换会话时串线；搜索及原文加载通过请求序号避免旧结果覆盖。Markdown 导出保留引用链接、页码、图号和模式。文档阅读器按原文页码分段，支持正文搜索高亮及 `/api/asset` 原图预览。社区 DeepSeek 鲸鱼娘素材在 `static/ARTWORK-LICENSE.md` 及随附许可中署名。

### 6.3 Watcher

- 轮询目录（默认 10 s），比较 `(mtime, size)` 快照；
- 变更文件调用 `parse_document`，删除文件清理对应解析目录；
- 每轮调用 `build_index(incremental=True)`；
- 事件写 `data/watch.log`（JSONL）；
- `--once` 便于测试与手工触发。

## 8. 模型端点协议

### 8.1 配置

```bash

```

### 8.2 端点约定

| 能力 | 方法 | 路径 | 响应关键字段 |
| --- | --- | --- | --- |
| Chat | POST | `/chat/completions` | `choices[0].message.content` |
| VL | POST | `/chat/completions` | 同上（content 含 image_url） |
| Embedding | POST | `/embeddings` | `data[].embedding` |
| Rerank | POST | `/rerank` | `results[].{index, relevance_score}` |

- 各能力独立记录失败：HTTP Embedding / Reranker 明确抛错；Chat 可回到抽取回答，VL 可回到 Mock 释义。失败不会将其他能力切换为 Mock；
- 端点不含 `/v1` 时由 `BASE_URL` 自行配置；代码只拼接相对路径；
- 不在代码/日志中输出 API Key。

### 8.3 Mock 边界（必须明示）

Mock 仅保证：

- 端到端链路可跑通；
- 单元/集成测试可复现；
- 输出格式与真实模式一致。

Mock **不保证**：

- 语义泛化能力；
- 真实图片理解能力；
- 生产检索质量指标。

因此项目书中的 1.0 指标仅对演示集与 Mock 链路负责；生产上线必须切换真实端点并重建索引。

## 10. 性能与容量

| 环节 | 当前实现 | 复杂度/备注 |
| --- | --- | --- |
| 解析 | 逐文件、逐页 | 线性；VL 调用是主要时延 |
| 切片 | 线性扫描 | O(字符数) |
| 建库 | 批量 embedding（16/批） | 线性；增量复用 |
| 稠密召回 | 全量余弦 | O(N·d)；万级 Chunk 可换向量库 |
| BM25 | 倒排 tf/df | O(查询词 × 候选) |
| 稀疏 | 稀疏点积 | O(非零项) |
| 精排 | 候选 24–40 条 | 真实 Reranker 时延为主 |
| 存储 | JSON | 演示 32 块约 0.6 MB；规模大时换 SQLite/向量库 |

## 11. 扩展点

1. **PDF 矢量图渲染**：接入 PyMuPDF，对含 drawings 的页面渲染为位图后送 VL；保持 `ImageInfo` 契约不变。
2. **向量库替换**：`Retriever` 的稠密召回替换为 FAISS/Milvus/pgvector，接口仍返回 `{chunk_id: score}`。
3. **真实 BGE-M3 稀疏**：将 `sparse.json` 的模拟权重替换为模型输出的 `{token: weight}`，RRF/精排不变。
4. **无头 Agent 服务**：`web.server` 的 `/api/ask` 内部改调 `claude -p` / `nga run`，`WebQueryResponse` 不变。
5. **多用户/权限**：在入口层增加租户与 ACL；索引按租户分区；下层契约不变。
6. **OCR 兜底**：扫描版 PDF 先走 OCR（PaddleOCR/Tesseract），再走现有解析链路。

## 12. 已知限制

- `.doc`（OLE 旧格式）未直接支持，需先转 `.docx`；
- DOCX 无固定分页，页码为估算值，已在 `page_mode` 与回答中标注；
- 矢量图（EMF/WMF/SVG/TIFF）当前跳过读图并告警；
- Mock Embedding 基于词面哈希，不等价于语义模型；
- 演示语料为虚构的 FE_HEART 场景，仅用于验证系统能力，不代表真实产品文档；
- Web 为单机本地服务，未做多用户鉴权与并发压测。

## 2026-10-29：真实 API 接入补充

- `ModelConfig` 新增 `embed_mode / rerank_mode / chat_mode / vl_mode`，留空继承全局；聊天新增独立 `chat_base_url / chat_api_key`，留空继承通用配置。密钥字段不参与 dataclass repr。
- `ModelHub.is_mock_for(capability)` 查询单项能力，`mode` 为 `mock / http / mixed`。`status()` 附各能力的模式和 `mock / configured / verified / degraded` 状态；状态查询不发探测请求。仅同一 Hub 内已成功调用的能力可标为 verified。URL 状态去除用户信息与查询参数。
- HTTP Embedding 响应按 `data[].index` 排序，校验条数、重复索引、维度及有限数值。HTTP Reranker 显式设置 `top_n`，要求响应覆盖全部候选并恢复顺序。两者错误直接抛出，不能返回 Mock 结果冒充真实模型。Chat 空内容视为失败，允许回到有证据的抽取回答；能力失败互不污染。
- 索引模型名必须与当前查询 Embedding 相同，即使向量维度相同也不能混用。建库按 Embedding 自身模式记录元信息；HTTP 失败时不覆盖已有三件套。稀疏路标记为 tfidf-local；旧索引可继续读取。
- Gitee 的 bge-m3 公开规范只定义 dense embedding，不提供稀疏权重字段，暂未接入学习型 sparse。
- `probe` 只测显式 HTTP 能力，Mock 明确跳过；空返回、缺失候选或非有限值判失败，所有诊断去除通用和聊天密钥。Web 只称已配置，不把配置状态写成已连接。
- 平台协议和当前本机鉴权状态见 [模型接入记录](05_模型接入记录.md)。
